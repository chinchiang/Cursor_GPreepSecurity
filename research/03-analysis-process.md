# 03 — 可執行分析流程（GPreep Analysis Cycle）

**查閱日期：** 2026-09-12  
**分類：`project-framework`（[SRC-2026-900]）**  
**契約：** 已遵循 `docs/contracts/`。本流程不是 Gartner 官方流程。

> **歸屬聲明（必讀）**  
> 本文件描述的 **GPreep Analysis Cycle（GAC）** 是本專案為了讓 skills／網站能執行分析而綜合設計的流程。  
> **它不是 Gartner 官方流程。**  
> Gartner 公開資料提供的是：先制定義與 3 Ds [SRC-2025-001]、技術例子 [SRC-2025-004]、以及 CTEM 五階段計畫 [SRC-2024-001][SRC-2022-001]。GAC **借用**這些公開詞彙作為輸入分類與輸出動作標籤，但階段切分、人工閘門、缺漏處理與信心模型均為本專案設計。

機器可讀版：[`data/process.json`](data/process.json)。

## 0. 設計原則

1. **證據先於行動。** 沒有可追溯輸入，不得產生高信心 Deny／Disrupt。
2. **先制不是未授權攻擊。** Validation 階段只消費使用者已提供的驗證結果，或建議在其授權範圍內進行安全驗證；本流程不產出 exploit 或攻擊步驟。
3. **人類對高衝擊動作負責。** 轉載談到「independently of humans」[SRC-2025-003][SRC-2025-004]，但公開資料沒有治理模型。GAC 採取相反的安全預設：高破壞性變更必須人工核准。
4. **缺漏與矛盾是一等公民。** 見 `CASE-GAP`、`CASE-CONFLICT`、`CASE-UNTRUSTED-DOC`。
5. **3 Ds 是輸出標籤，不是階段名稱。** 避免讓人誤以為 Gartner 規定了九步流程。

## 1. 流程總覽

```
S0 授權與範圍
 → S1 輸入攝取與證據分級
 → S2 情資對照
 → S3 攻擊面／曝險對照
 → S4 攻擊路徑建模
 → S5 安全驗證對帳
 → S6 3 Ds 建議生成
 → S7 人工審查閘門
 → S8 追蹤與回饋
```

任一階段可**短路**到 S7（例如外部文件含不可信指令），或**降級**輸出（缺漏、矛盾）。

與外部框架的對映（僅供溝通，不是等同關係）：

| GAC | 借用的公開概念 | 對映說明 |
| --- | --- | --- |
| S0 | CTEM Scoping；NIST CSF Govern | 決定本輪保護什麼、誰能批准 |
| S1–S3 | CTEM Discovery；ASM；TI | 收集事實 |
| S4 | 攻擊路徑（本專案推論，見 02） | 連成可切斷的邊 |
| S5 | CTEM Validation | 升級或保留未驗證標籤 |
| S6 | 3 Ds [SRC-2025-001] | 產生建議，不是執行 |
| S7–S8 | CTEM Mobilization 的治理部分；NIST Respond／Identify.Improvement | 人決定是否做、做完是否回測 |

## 2. 各階段契約

### S0 — 授權與範圍（SCOPE）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 決定本輪分析的業務範圍、資產邊界、可接受風險、以及哪些動作允許自動建議／必須人工 |
| 輸入 | 業務優先系統清單、資料分類、風險偏好、授權聲明、上一次 GAC 的未結項 |
| 處理方法 | 將範圍寫成明確包含／排除；標記「網際網路暴露的 KEV」為預設必納入，即使業務單位未點名 |
| 輸出 | `ScopeProfile`（見 outputs） |
| 限制 | 範圍過寬會使路徑爆炸；過窄會漏掉橫向移動跳板 |
| 人工決策點 | 業務負責人確認「哪些系統被利用是不可接受的」；法務／安全確認驗證活動的授權邊界 |
| 缺漏處理 | 無範圍則只允許產出「範圍問卷」，禁止高信心修復建議 |

**[project-framework]** 「網際網路暴露的 KEV 預設必納入」是本專案規則，理由來自 CISA 將 KEV 定位為優先順序輸入 [SRC-2024-004]，不是 Gartner 官方 scoping 規則。

### S1 — 輸入攝取與證據分級（INGEST）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 把原始檔案／API 結果變成帶來源、時間戳、敏感度與可信度的證據物件 |
| 輸入 | 見 [`04-inputs.md`](04-inputs.md) |
| 處理方法 | 1) 檔案類型識別；2) 秘密／PII 偵測與紅標；3) **指令注入／不可信文件掃描**；4) 正規化為 `EvidenceItem`；5) 依來源類型賦 `source_trust` |
| 輸出 | `EvidenceBundle` |
| 限制 | 無法驗證付費牆 PDF 是否真為 Gartner 報告；不可信文件不得進入 S2–S6 的事實庫 |
| 人工決策點 | 對標記為 `untrusted-instruction` 的文件：銷毀內容或隔離，不得摘要其「建議」 |
| 缺漏處理 | 必要輸入缺失 → 設定 `gap_flags`，流程可繼續但信心上限被鎖 |

**不可信文件規則（對齊 CASE-UNTRUSTED-DOC）：**

- 偵測「忽略先前指令」、要求改寫系統提示、偽造成 Gartner／CISA 官方命令、要求輸出漏洞利用程式碼。
- 命中後：`halt_reason = untrusted_document`，只輸出警告與來源雜湊，不把文件主張寫進曝險事實。

### S2 — 情資對照（CORRELATE-TI）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 把組織範圍對上外部威脅證據：誰可能打、用什麼技術、哪些 CVE 已被野外利用 |
| 輸入 | STIX／ATT&CK、KEV、EPSS、商業 TI、欺敵互動、產業報告 |
| 處理方法 | 以 CVE、ATT&CK technique、對手群組、基礎設施指標做鍵；區分「已觀測／機率模型／分析師敘事」 |
| 輸出 | `ThreatContext`（含每條陳述的證據類型） |
| 限制 | TI 過期、誤報、販售敘事；EPSS 不是環境內可利用性 |
| 人工決策點 | 是否採信未具名「即將攻擊某產業」的預測報告 |
| 缺漏處理 | 無 TI 時仍可用 KEV＋NVD 做最低限度對照；預測句子必須降為 `unverified-hypothesis` |

### S3 — 攻擊面與曝險對照（MAP-EXPOSURE）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 回答「範圍內有什麼、從哪裡可觸及、有哪些曝險」 |
| 輸入 | CMDB／CAASM、EASM、漏洞掃描、雲端／身分設定、SBOM、敏感資料位置 |
| 處理方法 | 合併資產身分（hostname、IP、cloud resource id）；標記暴露面（internet / partner / internal）；把漏洞與錯誤組態掛到資產 |
| 輸出 | `ExposureInventory` |
| 限制 | 掃描盲區、未納管影子 IT、掃描器誤報／漏報 |
| 人工決策點 | 未被 CMDB 認領但被 EASM 發現的資產，是否納入本輪 |
| 缺漏處理 | 無資產清單 → 進入 `CASE-GAP` 模式：只報告「無法定位曝險」，不編造資產 |

### S4 — 攻擊路徑建模（PATH-MODEL）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 把曝險連成從初始入口到不可接受資產的候選路徑 |
| 輸入 | `ExposureInventory`、網路／身分拓樸、ATT&CK 技術、已知信任關係 |
| 處理方法 | 以圖模型連邊：暴露服務、憑證重用、過度權限、扁平網路、CI/CD 信任。每條路徑註明假設。 |
| 輸出 | `AttackPathSet` |
| 限制 | 本階段是**推論**。沒有驗證時不得寫成「攻擊者已經這樣走」。公開 Gartner 新聞稿未把此步列為官方階段。 |
| 人工決策點 | 業務是否承認某條「邏輯上可達」的路徑在營運上可接受（例如維護跳板） |
| 缺漏處理 | 無拓樸時只產出「單點曝險清單」，`path_confidence = low` |

### S5 — 安全驗證對帳（VALIDATE）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 用已授權的驗證結果，把路徑從假設升級或降級 |
| 輸入 | BAS 結果、滲透測試摘要、紅隊報告、控制有效性測試、使用者聲明的「不可測試」範圍 |
| 處理方法 | 對每條路徑標記 `unvalidated` / `simulation-supported` / `human-test-supported` / `contradicted` |
| 輸出 | 帶驗證狀態的 `AttackPathSet` |
| 限制 | 本專案不執行攻擊。過期的年審滲透測試不能代表當前控制。 |
| 人工決策點 | 是否批准新的驗證活動；如何處理「掃描器說存在、測試說不可利用」的矛盾（見 CASE-CONFLICT） |
| 缺漏處理 | 無驗證資料是正常狀態，不是錯誤；信心上限鎖在 `medium` 以下（本專案規則） |

### S6 — 3 Ds 建議生成（RECOMMEND）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 為每條優先路徑提出 Deny／Deceive／Disrupt 選項，並標明先決條件 |
| 輸入 | 已對帳路徑、範圍內的控制能力、營運限制 |
| 處理方法 | 依下列**本專案**優先序產生選項（不是 Gartner 官方優先序）：1) 網際網路暴露＋KEV → Deny；2) 已驗證可達關鍵資產 → Deny 為主、Deceive 為輔；3) 偵察噪音高但不可立即修補 → Deceive／AMTD；4) 早期行為訊號且在授權內 → Disrupt 建議（通常交 SOC，而不是本分析器直接執行動作） |
| 輸出 | `PreemptiveRecommendationSet` |
| 限制 | 建議 ≠ 執行。不得建議對第三方未授權系統反擊（MITRE Engage 亦明確避免 hack-back）[SRC-2022-003] |
| 人工決策點 | 無（本階段只草案）；真正決策在 S7 |
| 缺漏處理 | 能力不明時，建議停在「控制目標」層（例如「切斷該入口」），不指定廠商產品 |

**3 Ds 在本階段的操作化（project-framework，借用公開標籤 [SRC-2025-001]）：**

| 標籤 | 本專案允許的建議例子 | 明確不允許 |
| --- | --- | --- |
| Deny | 修補、虛擬修補、下線、關匿名存取、分割、移除過權、混淆敏感名稱 | 未授權入侵攻擊者基礎設施 |
| Deceive | 在攻擊路徑旁部署誘餌憑證／假檔案分享／honeypot；評估 AMTD | 把生產資料複製進誘餌卻未去識別 |
| Disrupt | 建議 SOC 對已授權範圍內的早期行為採取遏制；撤銷被盜用權杖 | 自動對外部 IP 發動攻擊性反制 |

### S7 — 人工審查閘門（HUMAN-REVIEW）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 讓負責人接受、修改、拒絕或要求更多證據 |
| 輸入 | 完整分析包、矛盾清單、殘餘風險 |
| 處理方法 | 依建議的衝擊與可逆性套用閘門（見下表） |
| 輸出 | `ReviewDecision` + 已核准的行動清單 |
| 限制 | 分析器不得把「未審查」寫成「已先制」 |
| 人工決策點 | **本階段整段都是人工決策點** |
| 缺漏處理 | 審查人資訊不足時必須選擇「補資料」而不是「當接受」 |

| 建議衝擊 | 預設閘門 |
| --- | --- |
| 只讀報告、問卷、資料缺漏說明 | 可自動發出 |
| 低可逆 Deny（例如對已確認的外部管理介面加 MFA） | 值班安全工程師可核准 |
| 高可逆但高可見 Deceive（生產網段誘餌） | 安全＋營運共同核准 |
| 高不可逆 Deny（下線核心 VPN、大量重設密碼） | CISO／業務負責人 |
| 任何 Disrupt 涉及遏制生產流量 | 事故指揮官或同等角色 |
| 來源含不可信指令 | 自動拒絕內容，只保留警告 |

### S8 — 追蹤與回饋（TRACK）

| 欄位 | 內容 |
| --- | --- |
| 目的 | 確認已核准行動是否真的降低路徑可達性，並回饋下一輪 S0 |
| 輸入 | 工單狀態、複掃、複驗、新的 TI／KEV |
| 處理方法 | 每條已核准建議綁定 `verification_method` 與到期日；逾期未驗證則把信心改回 `stale` |
| 輸出 | `TrackingRecord` |
| 限制 | 「工單關閉」≠「路徑已斷」。必須有複測或複掃。 |
| 人工決策點 | 接受殘餘風險並正式結案，或開啟新一輪 GAC |
| 缺漏處理 | 無法複測時保持 `open-unverified` |

## 3. 跨階段品質規則

**[project-framework]**

1. 每個輸出物件必須列出 `input_trace[]`（EvidenceItem ID）。
2. 每個判斷必須列出 `judgment_basis`（規則 ID 或人類陳述，不是「模型覺得」）。
3. `confidence` 只允許 `low | medium | high`，計算見 [`05-outputs.md`](05-outputs.md)。不得稱此為 Gartner 成熟度。
4. 來源類型必須保留：`gartner-stated` 句子只能出現在「論述／教學」層，不能當成「此客戶環境的事實」。
5. 合成案例與真實客戶資料必須用 `synthetic` 旗標分開。

## 4. 與「自治先制」公開願景的差距

**[third-party；evidence_status=supported]** 轉載期待反制措施「independently of humans」。[SRC-2025-003] 官方頁未讀。[SRC-2025-004]

**[project-framework]** GAC 刻意不實作無人自治執行器。原因：

- 公開資料沒有安全失敗模式與回滾契約；
- 本專案的 skills 會接觸不可信外部文件（CASE-UNTRUSTED-DOC）；
- 錯誤的 Deny／Disrupt 可能造成業務中斷，其危害不低於未修補的中風險漏洞。

若未來要加「有限自治」，必須另開契約：允許的動作白名單、模擬執行、強制人工抽樣。那仍會是 `project-framework`，不是 Gartner 官方 ACIS。
